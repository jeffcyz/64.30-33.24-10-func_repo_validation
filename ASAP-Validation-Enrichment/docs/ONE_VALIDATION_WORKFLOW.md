# One Validation per Claude Session (recommended)

This is an alternative to the legacy S00-S18 workflow. Each fresh Claude conversation analyzes ONE numbered Validation ID and its continuation rows. It produces a compact, schema-compatible JSONL patch and QA JSON, not a rewritten master dataset.

The local Python tool keeps real files durable. No shared Claude memory, completed global Runtime Catalog, or 19-session setup is required.

## Private local inputs

Place these ONLY on your company computer under source/:

- validation_master_flat.json — the immutable 108-row source array; retain development_status.
- merged_scripting_manual.md — scripting runtime API authority.
- merged_user_manual.md — business/setup/periodic meanings.
- Releases-be4181818e.md — version/release caveats.
- schema_catalog.md — SQL metadata, NOT evidence of direct runtime accessibility.

The repo is PUBLIC. Do not commit source data, context packs, generated patches or QA artifacts. Use only an organization-approved Claude deployment.

Control files already supplied or generated locally:

- control/SPEC_SCHEMA.json — shared implementation_spec schema.
- control/ROW_REGISTRY.jsonl — run python tools/build_registry.py once if not present.
- control/PROJECT_STATE.json — source SHA-256 check; generated by build_registry.py. It is NOT a per-validation completion prerequisite.

## Quick start for record #20

From the ASAP-Validation-Enrichment project root, run:

    python tools/build_registry.py
    python tools/single_validation.py prepare --id 20

Expected new local text files:

    context_packs/by_record/R020_CONTEXT.txt
    context_packs/by_record/R020_EXECUTE.txt

Open a NEW Claude conversation. Paste prompts/SINGLE_VALIDATION_HEADER.md first, then the entire R020_CONTEXT.txt, then R020_EXECUTE.txt last. Do not execute before all sources have been pasted.

When Claude returns the artifacts, save them locally:

    patches/by_record/SPEC_R020.jsonl
    qa/by_record/QA_R020.json

Then run:

    python tools/single_validation.py validate --id 20
    python tools/single_validation.py merge --id 20

Output is final/validation_master_enriched.json with only #20 and its continuation records enriched. Next use --id 21 in another NEW Claude conversation, repeat the same steps, and keep existing specs.

When re-running an already enriched record:

    python tools/single_validation.py merge --id 20 --replace

The merge creates a backup before replacing an existing output. The original source/validation_master_flat.json remains unchanged.

## Full documents vs selected sections

By default prepare includes all four existing Markdown files (FULL_DOCUMENT) as source blocks. It does not attempt to summarize or extract them. If their total size is near your Claude context limit, select excerpts instead:

    python tools/single_validation.py prepare --id 20 --manual-mode selected --include ASAP_SCRIPTING_MANUAL:source/chunks/SM-001.md --include ASAP_USER_MANUAL:source/chunks/UM-005.md

In selected mode, list each supplied chunk explicitly with its authoritative SOURCE_ID and a stable chunk name. Be honest about missing evidence; unresolved access stays null.

## Source authority and non-invention

- Validation Master: intended business rules, exact WARNING, parent conditions, unchanged THRESHOLD and development_status.
- Scripting Manual: documented runtime objects, signatures, access expressions and limits.
- User Manual: field semantics, lifecycle and business context.
- Release Notes: version-dependent availability, not automatic current-version proof.
- SQL Catalog: tables and columns, never by itself a runtime API.
- Every claim of a verified Runtime symbol needs an actual pasted source chunk and a short matching excerpt.
- No guessed Runtime symbols, formulas, prior-period access, numeric zero defaults or tolerance values.
- Documentation readiness is separate from script development status.

## Patch format and association

One JSONL object per source row:

    {"row_key":"R020","source_row_sha256":"<exact registry hash>","implementation_spec":{...}}

If record #20 has continuation row C020-01, the patch also needs exactly one line with row_key C020-01. The hash must match ROW_REGISTRY if supplied. No original business fields appear inside the patch. Spec matches control/SPEC_SCHEMA.json.

QA_R020.json is a separate report and is NOT merged into the main JSON. Main source rows keep their exact order and all existing fields.

## Validation scope

The local validator checks JSONL parsing, row coverage, duplicate keys, source fingerprints, and the supported JSON Schema types, enums and required fields. It cannot certify that a claimed ASAP Runtime API actually exists. Review manual evidence before treating a spec as ready.

Do not add a status field named developed automatically: the existing development_status is immutable in this workflow.

## Legacy compatibility

The original 19-session prompts, tools/prepare_session.py and tools/merge_specs.py remain available. They are NOT used for the one-record flow. In particular the legacy merge_specs.py expects eight SPEC_PATCH_XX.jsonl files. Use tools/single_validation.py for the new workflow.
